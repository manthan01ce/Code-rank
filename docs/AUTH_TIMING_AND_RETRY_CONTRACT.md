# Authentication timing and retry contract

Existing endpoints and JSON payloads remain compatible. POST /api/auth/login fails closed with 503 and Retry-After: 5 when its limiter is unavailable, retains 429 for actual throttling, and prevents caching of session responses. The browser waits at most 12 seconds for the entire response and never automatically replays a login. This is a client wait bound, not a claim that an in-flight session write is cancelled.

Only the side-effect-free login user lookup opts into database read retry: at most three transient-connection attempts in one 2500 ms budget with 250/500 ms backoff. Other queries and transactions are single attempt by default. Native transaction completion is definitive. A query timeout cannot prove that a write did not commit; clients must not automatically replay uncertain writes.

Standard Server-Timing response headers contain only allowlisted duration labels and numeric milliseconds. Login labels: rate_limit, lookup, password_compare, session_commit. Admin account-creation labels: auth, validation, password_hash, database_commit. The latter includes round trip, DB function work, advisory-lock waiting and commit; it does not claim to isolate lock wait or commit at the database engine level. No tokens, passwords, account identifiers or SQL enter timing headers or performance JSON.

The baseline/candidate CI workflow uses the same browser harness, production builds, fresh migrated disposable PostgreSQL databases, real Redis and Docker, and Chromium. Each revision requests 20 successful sign-ins and 20 successful UI account creations for each of fresh-browser-context and reused-context conditions. Fresh context means cold browser storage/cache, not cold application/database processes. Browser readiness includes successful backend data responses and a visible dashboard; observed LCP is collected with PerformanceObserver and is provisional until capture. Account creation records response-to-confirmation including credential PDF generation; downloads are ephemeral and not copied into reports. Performance traces/screenshots/videos are disabled to avoid persisting credentials. Failures are not filled in as successful samples.

Production Neon credentials, hosting repair, engine-level lock/commit traces and true server/database-cold runs still require the configured deployment and controlled infrastructure. CI is an isolated test-stack measurement, not a restored public production deployment.
